## Regeneration

1. Dispatch `settings-library-oracle` on a branch at the harness commit and download the
   `p1-002-generated-settings` artifact with `gh-axi run download`.
2. Copy `payload/settings/config.json`, `payload/settings/fullscreenConfig.json`, and
   `payload/settings/windowPositions.json` byte-for-byte to `tests/golden/settings/`.
3. Copy the `library-export` output of `tests/fixtures/v10/library` byte-for-byte to
   `tests/golden/library/` (the command is a raw copy, so these equal the approved fixture
   bytes; the fixture pin is verified first).
4. Write `tests/golden/settings-library.sha256` in payload order:
   `<lowercase sha256><two spaces><path relative to tests/golden>`.
5. Push and let the PR's `validate` job run `Verify.ps1 -Mode Validate` against the committed
   fixture, manifest and goldens. No mode writes or auto-accepts protected paths.

## What these goldens prove

- On the Windows runner, at the harness commit above, v10 public APIs produced exactly these
  settings bytes from the pinned seeds, with the seeded public values surviving
  serialization.
- Within that run, save/reload/save and an independent repeat from the seed were
  byte-identical; the earlier run above produced the same three settings hashes.
- The 21-file inventory and `settings-library.sha256` cover exactly the approved paths. The
  `Validate` mode is the acceptance consumer: it reproduces the 21 payloads, compares them
  byte-for-byte to these goldens, and requires the fixture tree and goldens to stay
  unchanged during the run.
- The library payloads are the approved v10 fixture bytes, unmodified.

## What these goldens do not prove

- They do not show that the Linux port emits these bytes; this unit compares the oracle to
  itself, not to the port.
- They do not prove the semantic contents or validity of the LiteDB files. `library-export`
  is a raw copy and never opens the database.
- They do not cover other ambient conditions (locale, DPI, GPU, multiple monitors, other
  Windows versions). The machine-dependent primary-screen index is supplied as seed data,
  not derived, so the default `Monitor` computation is not exercised.
- They do not cover settings or fixture mutations beyond the verifier's explicit negative
  checks. Comparator negatives in `Test-Validation.ps1` run on synthetic unit bytes, not on
  these goldens.
- They are not acceptance by themselves: tests/golden changes still require the
  `oracle-change` label, independent review, and merge.
